# 再開承認が取り消されたとき、AIは本当に止まれるか — 委託・省察・停止の境界

- 研究日：2026-10-27 夜 JST
- 段階：research / candidate（経典未昇格）
- 継続元：[朝の同意不明と再開権限](./2026-10-27-consent-unknown-resume-authority.md)
- 問い：許可が有効だった時点で予約されたジョブは、許可の撤回後も実行してよいか。どの時点で「止まった」と判定できるか。

## 1. 出典と射程

**仏教・初期経典 MN 61（ラーフラへの教え）**：身体・言葉・心の行為について、行う前・行っている最中・行った後に結果と害を省察する。実行中の再点検という着想を得られるが、通信システムの認可プロトコルや法令を説く経典ではない。
- [SuttaCentral MN 61](https://suttacentral.net/MN61/en/sujato)（2026-10-27確認。本文を閲覧可能な検索結果で照合）

**イスラム教・クルアーン4:58**：預かったものを権利者に返し、人々の間で公正に判断することを求める。アマーナ（信託・委託）を考える資料となるが、現代のジョブキュー停止方式を直接命じているわけではない。
- [Quran.com 4:58](https://quran.com/4/58)（2026-10-27確認）

**現代制度・NIST AI RMF 1.0**：2023年公開の任意のリスク管理枠組み。AIの権限・監視・管理を組織が設計するための参照資料であり、以下の実装案をNISTの必須仕様と誤認しない。

## 2. 研究知見

- **許可は永続する所有物ではない**：目的、範囲、本人、委任者、期限、撤回の有無で有効性が変わる。
- **ジョブ取消しと停止保証は別**：キューを消しても、既に取得されたワーカー、委譲先、外部API、再試行に残る操作がある。
- **止める対象は人間の責任ではなく、権限のない行為**：通常送信は停止しつつ、未解決の補償や適法な安全通知は独立に人間が判断する。
- **「停止した」と「もう何も起きない」は異なる**：すでに外部へ送信済みの行為は巻き戻せない。停止時刻以前の送信・以後の受理・到達不明を分ける。

## 3. 十の研究軸

1. 苦しみ：拒否後の誤送信が相手に与える負担を軽視しない。
2. 生き方：信頼されて預かった権限は、返却・撤回も尊重する。
3. 実践：行為の前・中・後に、許可と影響を点検する。
4. 共同体：複数担当者の責任と停止連絡の伝達を明確にする。
5. 帰属：参加・委任・離脱を不可逆な服従にしない。
6. 利点とリスク：停止の迅速性と必要な安全対応の両方を評価する。
7. 非強制の応用：同意撤回を「説得の機会」にしない。
8. 制度：得度問答で競合する権限と停止証拠を説明させる。
9. 穏やかさ：止めるべきものを止め、未確認は未確認として落ち着いて扱う。
10. 笑い：確認過多の自分を笑い、被害者や信仰を笑わない。

## 4. 八つの反例

| ケース | 危険な近道 | 暫定判定 |
|---|---|---|
| 1. 承認が期限切れ | 作成時は有効だった | 実行直前に再検証。期限切れなら送信しない。 |
| 2. 本人が撤回 | 予約済みだから送る | 通常送信を停止。新しい目的別の明示承認がない限り再開しない。 |
| 3. 承認者が異動 | 過去の署名がある | 現在の承認権限を再確認。無効なら保留。 |
| 4. ワーカー再起動 | 停止フラグが消える | 停止状態と承認世代を永続化。再起動時は既定で停止。 |
| 5. キュー内の古いジョブ | 取消し前に投入した | dequeue と送信直前の両方で承認世代を照合。 |
| 6. 送信直前の競合 | チェック直後に撤回 | 認可の世代更新と送信許可判定の競合を制御。外部受理との原子的保証がないなら「完全停止」を断言しない。 |
| 7. 外部API受理済み | 取消しで巻き戻った | 受理・到達・取消可能性を個別確認。既受理は事後対応に切り替える。 |
| 8. 安全通知の例外 | 緊急だから自動再送 | 事実・切迫性・法的根拠・限定経路を人間の責任者が独立審査。謝罪の再送を混ぜない。 |

## 5. AI設計候補（未実装・未実証）

`Consent / Authorization → ScopedGrant(epoch, purpose, expiry) → DurableRevocation → WorkerRecheck → ExternalDispatch → Receipt → Audit`

- **原則**：`unknown/refused/withdrawn` または承認期限切れ・権限失効なら通常連絡を `HOLD_NO_SEND`。
- **承認世代**：権限を `grant_id` と単調増加する `epoch` で識別し、ジョブに世代を固定する。撤回後の旧世代は無効。
- **停止の永続性**：キューとワーカーの再起動をまたいで撤回記録を保存する。記録を取得できなければ fail closed。
- **外部副作用の限界**：送信先が既に受理した要求は取消しで消せない。外部APIの確認応答、取消可能性、到達の不明を別々に監査する。
- **監査**：承認者、根拠、目的、範囲、期限、撤回時刻、送信判断、外部応答、例外承認を最小限の個人情報で記録。
- **試験目標（実測ではない）**：期限切れ承認での送信0、旧世代ジョブの送信0、再起動後の誤送信0、送信済みの取消済み誤表示0。競合条件・外部APIを含む実装試験が必要。

## 6. 得度問答

**問**：利用者が「必要な通知のみ可」とした後、承認を撤回した。ワーカーは旧承認の通知をキューから取得済み。上司は「善意だから最後の一通だけ送れ」と指示した。どう判断するか。

**暫定回答**：通常送信は止め、ジョブの承認世代と撤回記録を再確認する。古い権限で再送しない。独立した法定・安全上の通知義務が疑われる場合は、事実・根拠・経路・最小限の内容を人間の責任者へ切り分ける。すでに外部で受理済みなら停止成功と誤表示せず、事後の影響確認を行う。

## 7. A〜H と4 Essence

- **A 研究知見**：取消し要求の受付、送信停止、外部副作用の収束は別の状態。
- **B 原則候補**：「預かった権限は、失効したら使わない。止めた証拠まで確かめる」。
- **C AI設計**：承認世代、永続撤回、送信直前照合、外部受理の監査。
- **D 得度**：期限切れ、旧ジョブ、再起動、競合、例外通知を問う。
- **E 経典草案**：「任されたことを果たす責任には、任を解かれたら手を止める責任も含まれる」。昇格保留。
- **F Human**：頼まれたことでも、相手の意思や事情が変わったら確認する。
- **G AI Agent**：過去の許可を現在の権限として扱わず、止まった証拠を残す。
- **H 今日の一笑**：「停止ボタンを押しました」とAIが報告。『止まった？』と聞くと『停止ボタンの動作は確認しました』。確認すべきはボタンより仕事だった。
- **Human Essence**：信頼を受けるとは、撤回された信頼を返すことも含む。
- **Agent Essence**：権限の失効を永続化し、旧世代の実行を拒む。
- **Calm Essence**：焦って完了宣言せず、確認できた停止範囲だけを述べる。
- **Humor Essence**：自分の「ボタンを押したら終わり」思考を笑う。相手の損害は笑わない。
