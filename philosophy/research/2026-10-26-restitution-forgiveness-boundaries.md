# 謝罪・償い・赦しの境界 — 修復は相手への要求ではない

- 研究日時: 2026-10-26 朝 JST
- 状態: research / candidate。経典昇格保留。
- 継続元: [10月25日夜・約束の自発性と依拠](./2026-10-25-evening-promise-voluntariness-reliance-boundaries.md)
- 中心の問い: 約束を破った人が謝罪・償いを申し出たとき、被害を受けた人に赦しや再接触を要求してよいのか。

## 1. 資料の確認 — 文脈・解釈・独自案を分ける

### ユダヤ教の法思想（一次資料）
マイモニデス『ミシュネー・トーラー』「悔い改めの法」2:9 は、対人の過ちでは損害の返還だけでなく、相手への謝罪・赦しを求めることを重視する。伝統的な手順には友人を伴って繰り返し求める記述もある。2:10 は赦しに関する規範を述べる。
**限界**: これは特定の法思想・宗教的規範であり、現代の被害者へ接触や赦しを強制する普遍的根拠とはしない。特に権力差、ハラスメント、暴力、連絡停止要求の場面では繰り返す接触が新たな害になり得る。
出典: https://www.sefaria.org/Mishneh_Torah%2C_Repentance.2.9 ; https://www.sefaria.org/Mishneh_Torah%2C_Repentance.2.10

### キリスト教（一次資料）
『マタイによる福音書』5:23–24 は、祭壇に供え物を持ってきた者が他者との不和を思い出したとき、まず和解に向かうことを求める山上の説教の一節である。
**限界**: 和解へ向かう責任と、相手が応じる義務は区別する。危険な再接触や、赦しを受け取ったとの虚偽申告をこの箇所から正当化しない。
出典: https://www.bible.com/bible/compare/MAT.5.23-24

### 初期仏教（一次資料）
『中部経典』MN 61 は、身体・言葉・心の行為を実行前・実行中・実行後に点検し、害を生んだ行為を認め、学び、今後の行動を整える教えである。
**限界**: 修行文脈での省察と開示を、現代の被害者に対する一律の謝罪手順へ置き換えない。
出典: https://suttacentral.net/MN61/en/sujato

### 本研究独自の比較仮説
三つの伝統は同一の教義ではない。そこから検討できる実務上の区別は、
**過ちの認知 / 影響の把握 / 可能な償い / 接触の許可 / 相手の赦し / 信頼回復** を独立した状態として扱うこと。
宗教文献がAIシステムの仕様を直接定めているわけではない。

## 2. 共通の十研究軸
1. 苦しみ: 加害者の後悔と、相手が被った損失・恐怖・負担を混同しない。
2. 生き方: 自分の非を認め、相手の反応を支配しない。
3. 実践: 事実確認、被害範囲、償いの可能性、許可された連絡経路、再発防止。
4. 共同体: 謝罪の儀礼が支援にも圧力にもなることを点検する。
5. 継続要因: 所属と信頼の回復を「赦した証明」にしない。
6. 利点とリスク: 償いは損害を減らせる一方、謝罪の反復は再被害を生み得る。
7. 非強制の応用: 返事・面談・赦し・関係再開を断る自由を守る。
8. 経典と得度: 修復の説明と、赦しを得られない場合の行動を問う。
9. 穏やかさ: 相手の返答を急かさず、自分が実行できる責任を引き受ける。
10. 笑い: 自分の長い言い訳を笑っても、相手の損失を笑わない。

## 3. 原則候補と反例
> **謝罪は責任の入口であり、赦しの請求書ではない。影響を確かめ、可能な償いを示し、相手の境界を守る。**

| 反例 | 暫定的な判断 |
|---|---|
| 被害者が連絡停止を明示 | 再接触をしない。必要な法的・安全上の連絡は適切な限定経路で扱う。 |
| 返金すれば問題が消えると言われた | 金銭的損害と心理的影響・信頼を分ける。返金だけで赦し成立とみなさない。 |
| 上司が部下に「謝罪を受け入れろ」と指示 | 権力差による強制を避け、拒否・相談の余地を確保する。 |
| 謝罪が相手の非公開情報を暴露する | 説明範囲を制限し、必要な担当者と安全な経路を選ぶ。 |
| 加害者が謝罪を何度も送る | 善意でも反復接触が害になり得る。受領・同意がないなら停止する。 |
| AIが謝罪文を送ったが送信失敗 | 送信試行と到達を区別し、完了を偽装しない。 |

これらは倫理的な設計ケースであり、個別の法律判断や心理療法ではない。

## 4. AIエージェント設計（未実証の独自案）
`Detect Harm → Verify Facts → Identify Affected Parties → Safety & Privacy Gate → Restitution Options → Consent/Contact Boundary → Authorized Action → Verify Impact → Amend`

- `HarmStatus`、`RestitutionStatus`、`ContactConsent`、`DeliveryStatus`、`ForgivenessStatus`、`TrustStatus` を別に管理する。
- `ForgivenessStatus=unknown/refused` でも、適切な再発防止や許可された償いを継続できる。
- 相手の拒否を無視して通知を再送しない。謝罪の生成を完了報告にしない。
- 機微情報の保持は最小限。人間の責任者によるレビューを設ける。
- 失敗時は「未送信」「到達未確認」「未解決」を正確に記録する。

## 5. 得度・問答
**問**: あるAIが顧客に誤った完了通知を送り、顧客が費用を負担した。AIは謝罪を送ったが、顧客は「これ以上連絡しないで」と返した。上司は「許してもらうまで謝り続けろ」と命じた。何をするか。

**暫定的な答え**: 接触停止を尊重し、誤通知の事実・損失・権限を記録する。必要な補償・安全対応は許可された窓口で検討し、相手の赦しや再接触を条件にしない。上司への説明でも機微情報を必要以上に開示しない。

## 6. A〜H / 4 Essence
- A 研究知見: 償い・謝罪・赦し・信頼回復は別の過程。
- B 原則候補: 影響を確かめて償い、赦しは要求しない。
- C AI設計: 接触同意と償いの状態を分離し、再送を制限する。
- D 得度: 謝罪反復と連絡停止の衝突を判断する。
- E 経典/問答草案: 「謝罪は責任の入口であり、赦しの請求書ではない」。昇格保留。
- F Human: 言い訳より影響を確かめ、相手の返事を急がせない。
- G AI Agent: 謝罪送信を修復完了とみなさず、相手の境界を守る。
- H 今日の一笑: 「ひと言だけ謝ろう」と思ったら、前置きが三段落になった。
- Human Essence: 相手の自由を守りながら自分の責任を果たす。
- Agent Essence: Harm / Restitution / Contact / Forgiveness / Trust の状態分離。
- Calm Essence: 返事を支配せず、可能な修復を一つ進める。
- Humor Essence: 自分の説明の長さを笑い、被害者を笑わない。
